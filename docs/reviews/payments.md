# Payments & credits review

Independent review of billing (Stripe and mock providers, webhooks, subscriptions, refunds) and the credit ledger (job debits and refunds, likeness, blocked and missing refunds, team transfers, admin adjustments). This is a report only: no source files were changed.

**Scope read:** `src/server/billing/**`, `src/providers/payment/**`, `src/app/api/billing/**`, `src/app/api/webhooks/payments/**`, `src/server/credits/ledger.ts`, `src/server/jobs/engine.ts` (+ `costs.ts`, `handlers/generate.ts`, `handlers/talking-video.ts`, `handlers/upscale.ts`), `src/server/media/service.ts`, `src/server/teams/credits.ts`, `src/server/admin/{jobs,schemas,stats,revenue}.ts` and the admin routes, `src/server/account/delete-account.ts` (subscription step), `src/config/{plans,credits,rate-limits}.ts`, `src/lib/env.ts`, `docs/DECISIONS.md`.

**Method:** code reading, plus probe tests run against the PGlite harness. The probes live outside the repo: the scratchpad `probes/*.probe.ts` files were run with a dependency-free vitest config whose root is the repo. The existing suites `tests/unit/billing` and `tests/unit/teams/credits.test.ts` pass (96 tests). Findings confirmed by a probe are marked **[probe]**.

Severity: **High** means money or credit loss or harm to paying customers with a realistic trigger. **Medium** means abuse or loss that needs particular conditions. **Low** covers robustness, accounting or UX problems.

## Verified OK

- **Webhook authenticity:** Stripe is verified with `constructEventAsync` over the raw body (`route.ts` reads `req.text()`). The mock HMAC key is purpose-bound and derived from `authSecret` (required in production) and compared with `timingSafeEqual`.
- **Provider isolation:** `/api/webhooks/payments/[provider]` returns 404 unless the provider is the configured one. `/billing/mock-checkout`, `/api/billing/mock/complete` and `/api/billing/mock/cancel` all return 404 in Stripe mode. Mock checkout ids are HMAC-signed, bound to the user id and expire after 24 h, so they cannot be re-targeted at another account.
- **Duplicate webhooks:** the same event id gives `duplicate` once processed. The same checkout delivered under another event id (completed plus async_payment_succeeded) is blocked by the ledger key `payment:<checkoutId>`. Invoice grants use the key `invoice:<id>`.
- **Retries and transient failures:** effects and the `processedAt` mark commit in one transaction, so a failure rolls everything back and the redelivery re-claims the row through `error is not null`. No half-applied grants (covered by existing tests). `RetryablePaymentEventError` and retryable `parseWebhook` errors map to 500.
- **Out-of-order events:** an older `subscription.updated` is ignored, `canceled` is terminal, a late `incomplete` cannot overwrite a paid state, and `invoice.paid` can arrive before `checkout.completed` or `subscription.created`. A stale `invoice.payment_failed` is ignored. `deleted` arriving before `updated` is handled. A late `invoice.paid` on a canceled subscription grants the paid credits without reviving the subscription.
- **Dunning and cancellation:** `past_due` keeps the plan; `unpaid`, `paused`, `incomplete` and `incomplete_expired` (mapped to canceled) drop it. With `cancel_at_period_end` (or `cancel_at`) the plan is kept until `deleted`.
- **Grants:** proration invoices (`subscription_update`) grant nothing. Yearly plans grant 12× up front, and renewals grant again.
- **Refunds:** the cumulative `amount_refunded` is handled. Partial then full, and out-of-order partials, reverse no more than the payment granted. The reversal is idempotent per event. The revenue rows (negative refund rows, original marked `refunded`) are never double-counted. A refund may take the balance below zero, by design.
- **Async payment methods for credit packs:** an `unpaid` completed session is ignored, `async_payment_succeeded` grants, and `async_payment_failed` grants nothing. For subscription mode the plan follows the subscription status, and credits are granted only by `invoice.paid`.
- **Metadata:** the user id, plan, interval and pack id in our sessions are set on the server, and the checkout item is validated against the catalog with a zod enum. Users cannot change them. Quantity is fixed at 1. Promotion codes are the only lever on price (PAY-11).
- **Stripe customer:** the stored customer is reused per user, and a fresh customer is created on a user's first checkout (`customer_creation: always` for packs). The portal uses only the user's own stored id (but see PAY-10).
- **Account deletion:** subscriptions are canceled at the provider (failures are reported to the operator). Checkout and subscription events for a deleted account are acknowledged with a note.
- **Ledger:** a per-user `SELECT … FOR UPDATE` serializes debits, so the balance never goes negative except through `purchase_reversal`. There is a unique idempotency key with a cross-user conflict check, `Number.isSafeInteger` validation, and a zero delta writes nothing. Postgres `int4` raises on overflow instead of wrapping, and admin and transfer amounts are capped at ±1e6. Lock order (job → user, payment or subscription → user, sorted users for transfers) has no cycles.
- **Jobs:** the debit is in the same transaction as the job insert. `refundJob` caps the refund at `charged − refunded` under the job row lock, with idempotent tags. `failJob` refunds the remainder ("final") and repairs a run that crashed before refunding. Partial ingestion followed by failure cannot refund twice. Jobs stuck in `queued` or past their timeout are failed and refunded.
- **Batches:** creation stops at `insufficient_credits`, each child job is charged individually, and the batch total is trimmed. Batch `quality` excludes `draft`. The draft limiter still applies when batches skip the other rate limits.
- **Instant multiplier:** computed on the server in `handler.plan` and applied through API, UI and batches alike. A ready model's mode cannot change (`TRAINABLE_STATUSES = collecting, failed`), so it cannot be switched between plan and submit.
- **Draft re-render:** `fromDraftMediaId` forces `numImages=1`, rejects `quality=draft`, and requires the user's own draft image. Cost is 1 image at the requested quality (×2 for instant).
- **Likeness refunds:** capped per image at `floor(charged/expected)`. Upscale scores likeness only when the source passed the threshold, so refunds cannot chain.
- **Team transfers:** owner only, to an active member, a positive safe integer up to 1e6, both entries in one transaction with sorted locks, and the sender cannot overdraw.
- **Admin:** adjustments must be non-zero integers within ±1e6, require a note, cannot take a balance below zero and accept an optional idempotency key. An admin job refund happens at most once per job (tag `admin`) and is capped.
- **Signup bonus:** idempotent per user (`signup:<id>`).
